# 참가자 웹앱 설계

## 1. 프로필 생성

참가자가 닉네임·비밀번호·성별을 입력하면 클라이언트가 `createProfile` 요청을 보냅니다. 서버는 입력과 닉네임 중복 여부를 검사하고, 비밀번호를 무작위 salt와 PBKDF2-SHA256으로 해시한 뒤 UUID 참가자 ID와 임의 세션 토큰을 생성합니다.

세션 토큰만 브라우저 `localStorage`에 저장되며 프로필과 선택 기록의 기준 데이터는 D1에 유지됩니다. 다른 기기에서는 같은 닉네임과 비밀번호로 로그인해 별도 세션을 발급받습니다.

## 2. 상대 목록 생성

서버는 현재 참가자와 반대 성별이며 `is_sample = 0`인 실제 입장자만 조회합니다. 따라서 샘플 레코드나 같은 성별 참가자는 선택 목록에 표시되지 않습니다.

## 3. 선택 UI

1·2차에서는 빨간 하트와 노란 하트를 독립적으로 관리합니다. 두 상태가 같은 참가자 ID를 가질 수 있으므로 한 사람에게 두 하트를 모두 보내는 요구사항을 지원합니다. 3차에서는 노란 하트 UI를 제거하고 빨간 하트 한 개만 제출합니다.

## 4. 제출 검증

클라이언트는 필요한 하트를 모두 선택해야 확인 버튼을 활성화하고 제출 전 선택 대상을 재확인합니다.

서버에서는 다음을 다시 검증합니다.

- 세션 토큰이 실제 참가자와 연결되는지
- 여성은 1차, 남성은 2차, 모든 참가자는 3차에 참여하는지
- 선택 대상이 실제 반대 성별 참가자인지
- 이미 완료한 단계인지
- 1·2차는 빨강과 노랑, 3차는 빨강만 저장하는지

## 5. 단계 잠금과 즉시 결과

1차는 여성 전원, 2차는 남성 전원, 3차는 전체 참가자의 제출 수를 서버에서 비교합니다. 전원이 완료돼야 `event_state.current_stage`가 다음 단계로 바뀌며, 완료된 단계의 수신 결과만 API가 반환합니다.

## 6. 최종 결과

결과 조회 SQL은 현재 참가자를 `recipient_id`로 갖는 기록만 가져옵니다. 3차에서 내 발신 기록과 상대의 발신 기록이 서로 역방향으로 존재하면 `isMutual`을 반환해 매칭으로 표시하고, 상호 선택이 아니어도 나를 선택한 사람은 그대로 보여줍니다.

## 6. 모바일 UX

- 앱 설치 없이 링크로 접근
- 터치하기 쉬운 하트 버튼과 하단 선택 요약
- 선택과 제출을 분리해 오입력 방지
- 단계 진행 레일과 대기 화면 제공
- 모바일 폭을 기준으로 한 카드형 레이아웃
